# D07 — Raise the minimum WordPress version to 7.1

- Date, owner: 2026-10-06, Mateusz Zadorożny (maintainer)
- Context and the options weighed: issue #32 found that on WordPress 6.7 and later block-checkout error messages fell back to English on non-English sites, because `BlockCheckoutValidator::reload_textdomain()` called `unload_textdomain()`, which blocks just-in-time loading of the text domain for the rest of the request. The fix removes the unload and relies on `switch_to_locale()` / `restore_previous_locale()`, after which WordPress loads the domain for the active locale just in time. With `Requires at least: 5.0` that was not enough on every supported version: before 6.1 a locale switch unloads the domain for good and just-in-time loading looks only in `wp-content/languages`, so the first version of the fix carried a fallback, gated on the WordPress version, that loaded the translation file by hand. A review of that version found it fragile on WordPress 6.1 to 6.6 when a language pack for the plugin exists in `wp-content/languages/plugins`: there `load_plugin_textdomain()` returns as soon as it loads the pack for the site locale, before it registers the plugin's own `languages/` folder (`wp-includes/l10n.php` of WordPress 6.6), so on a German store with a German pack a shopper switched to `pl_PL` would get no Polish file. WordPress 6.7 registers the folder before that early return, and WordPress 6.8 and later register the `Domain Path` header themselves in `wp-settings.php`, but only for plugins activated per site: the loop that loads network-activated plugins does not (both loops read in 7.1.2). Two options were weighed: keep `Requires at least: 5.0` with the version-gated translation fallback for WordPress 5.8 to 6.6 and extend it to the language-pack case, which leaves one code path per range of WordPress versions, each needing its own check; or raise the minimum to a version where the core behaviour is enough on its own. Also relevant: WooCommerce 11.1.2, the current release in the WordPress.org directory on 2026-10-06, requires WordPress 7.0 (WordPress.org plugin information API), so a store that keeps WooCommerce current already runs WordPress 7.0 or later. This plugin itself needs only WooCommerce 7.2, so that does not cover stores on an older WooCommerce. No data on which WordPress versions installs of this plugin run was collected (A04).
- Decision and why: raise the minimum to WordPress 7.1 (`Requires at least: 7.1` in the plugin header and in `readme.txt`), released as 2.0.0, and keep only what WordPress core does, plus the one call core needs from a network-activated plugin: no translation code for older versions, and `load_plugin_textdomain()` only in the main plugin file, where since WordPress 6.7 it registers the bundled `languages/` folder and loads no file. One code path that WordPress itself maintains replaces version-specific workarounds. 7.1 rather than 6.8, the first version that reads `Domain Path` itself, is the maintainer's choice; the translation behaviour of this change was checked on WordPress 7.1.2 core only. Chosen by the maintainer on 2026-10-06; the agent had not recommended it.
- Consequences, and what would make us revisit it: the `load_plugin_textdomain()` call in the main plugin file stays, on `plugins_loaded` priority 5, because WordPress 7.1 registers the `Domain Path` folder itself only for plugins activated per site and a network-activated install would otherwise never find `languages/`; a language pack from translate.wordpress.org still takes precedence. Only `BlockCheckoutValidator`'s reload is gone (its `unload_textdomain()` / `load_plugin_textdomain()` pair, which caused #32), and so are the old-version code paths: the translation fallback for WordPress before 6.1 and the `strpos()` stand-in for `str_starts_with()` in `WhitespaceFilter`, which existed only because Plugin Check measured `str_starts_with()` (WordPress 5.9) against `Requires at least: 5.0`. Plugin Check is expected to report 0 errors and one warning, `load_plugin_textdomainFound` for the main-file call, which is accepted (1.x reported it for `BlockCheckoutValidator` too). Raising a minimum is a breaking change under `BACKWARD_COMPATIBILITY.md` §5, so the release is a major one with the reason in `CHANGELOG.md`, and the `readme.txt` Upgrade Notice for 2.0.0 names the new minimum. Sites below 7.1 can no longer update from WordPress.org: WordPress offers, installs and activates the plugin from the directory only where `Requires at least` is met, so they stay on 1.x, which keeps the #32 defect on WordPress 6.7 to 7.0. The GitHub updater of 1.4.x is the exception: it offers the latest GitHub release (`releases/latest`) with `requires` hard-coded to `5.0`, whatever the release's own header says, and caches the release for 12 hours (`git show master:src/Admin/GitHubUpdater.php`). A 1.4.x install on WordPress below 7.1 that checks while 2.0.0 is the latest release is therefore offered 2.0.0, and at least some update paths install it without re-reading the package header (in 7.1.2 core, `Plugin_Upgrader::upgrade()`, used by automatic updates and the single-plugin update screen, does not run `check_package()`, and automatic updates check only the offer's PHP requirement; older cores were not read). It then lands in the inert state below. The mitigation is release order: 1.5.0 (PR #36), which removes the updater, is released first and stays the latest GitHub release for at least 48 hours, preferably a week, before 2.0.0 ships: the 1.4.x updater caches a release for 12 hours (a release whose ZIP is not attached yet as well, and `release.yml` attaches the ZIP only after publishing the release), and WordPress refreshes plugin updates twice a day through WP-Cron, which on a quiet site waits for a visit; an install that took 1.5.0 has no updater left and never sees 2.0.0 from GitHub. An install still on 1.4.x when 2.0.0 ships, because it has no automatic updates and the 1.5.0 update was left pending or it never checked in that window, is offered 2.0.0 from then on. A 2.0.0 copy placed on such a site by other means (FTP, a deploy script, Composer, or that late 1.4.x update) boots nothing and shows administrators a notice naming the required and the running version (`Admin\DependencyChecker::is_wordpress_supported()`), so phone numbers are not checked there until WordPress is updated. Revisit if a store that cannot update WordPress needs this plugin, or if the WordPress.org directory requires support for older versions.
- Release mechanism: this repository's semantic-release (angular preset) cuts a major release only from a `BREAKING CHANGE:` footer in the squash commit; a `!` after the type cuts no release at all. The change therefore merges, after 1.5.0 has been released, with the subject `fix(checkout): keep block-checkout messages translated on WordPress 6.7+` and the footer `BREAKING CHANGE: requires WordPress 7.1 or later. On an older WordPress the plugin checks no phone numbers and shows administrators a notice.` That footer becomes the reason in `CHANGELOG.md` that `BACKWARD_COMPATIBILITY.md` §5 asks for.
- Status: active
