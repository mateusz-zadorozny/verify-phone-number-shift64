# D05 — Remove the GitHub self-updater before submitting to WordPress.org; updates come only from the directory

- Date, owner: 2026-10-06, Mateusz Zadorożny (maintainer)
- Context and the options weighed: D02 kept `src/Admin/GitHubUpdater.php` and deferred the question to the first WordPress.org review, because the directory's guideline on bundled self-updaters had not been read (A01). The updater hooked `pre_set_site_transient_update_plugins`, `plugins_api`, `upgrader_source_selection` and `upgrader_process_complete`, and queried `https://api.github.com/repos/mateusz-zadorozny/verify-phone-number-shift64/releases/latest`. The WordPress.org readiness audit (issue #31) read the guideline. Detailed Plugin Guideline 8, "Plugins may not send executable code via third-party systems", lists "Serving updates or otherwise installing plugins, themes, or add-ons from servers other than WordPress.org's" among what is not allowed (https://developer.wordpress.org/plugins/wordpress-org/detailed-plugin-guidelines/). The review team's common-issues page asks authors to "remove the checks you have in your plugin to provide for updates" (https://developer.wordpress.org/plugins/wordpress-org/common-issues/#update-checker). A Plugin Check 2.1.0 run on the 1.4.2 release build (WordPress 7.1.2, WooCommerce 11.1.2) reported the file as `plugin_updater_detected` (ERROR) and twice as `update_modification_detected` (WARNING). The updater also contacted api.github.com without opt-in and sent the site's home URL in its User-Agent, which guideline 7 ("plugins may not contact external servers without explicit and authorized consent") covers as well. The options were the three D02 had put to the maintainer: keep it and learn at review; keep it but disable it for directory installs; remove it.
- Decision and why: remove the updater, its unit test and its wiring before submission. Updates come only from WordPress.org. Keeping it would now lose a review round knowingly. Disabling it for directory installs would still ship the update code that the guideline and Plugin Check reject. The agent recommended removal after reading the guideline; the maintainer accepted that recommendation on 2026-10-06. Unlike D02, this decision rests on the guideline text and a Plugin Check run, not on a deferred check.
- Consequences, and what would make us revisit it: the plugin makes no outgoing HTTP requests. Installations running 1.4.2 or earlier from a GitHub release ZIP get one final update through the old updater: the latest GitHub release at the time they check, which no longer contains the updater. This works only while `.github/workflows/release.yml` keeps attaching an asset named `verify-phone-number-shift64.zip` to each GitHub release, because that is the name 1.4.2's updater downloads; when a Release run fails after publishing the release, `.github/workflows/wporg-deploy.yml` with `upload-zip` re-attaches it. After that, such installs receive updates only from WordPress.org, once the plugin is listed. WordPress.org matches installs by folder slug, so an install in a folder other than `verify-phone-number-shift64` (for example `verify-phone-number-shift64-master`) will not be offered directory updates and must be reinstalled from the directory. Verified on 2026-10-06 against the directory's update API, with other plugins because this one is not listed yet: a POST to `https://api.wordpress.org/plugins/update-check/1.1/` with a `WordPress/7.1.2` User-Agent offered an update to `query-monitor/query-monitor.php` but not to the same plugin in `query-monitor-master/`, `query-monitor-main/` or an arbitrary folder, and wp-crontrol, user-switching, akismet, woocommerce and wordpress-seo in `-master` folders were not offered one either. The one exception, `classic-editor-master`, looked like a server-side alias. The `shift64_phone_validation_github_release` transient left on upgraded sites expires within 12 hours; `uninstall.php` keeps deleting it. One of issue #11's four never-browser-verified behaviours, one-click update from a non-default directory, ceases to exist, so three remain. A01 is refuted. The update channel was never a protected surface in `BACKWARD_COMPATIBILITY.md`, so the removal ships as a minor release. Revisit if the plugin leaves or is closed in the directory, or if guideline 8 changes.
- Status: active
